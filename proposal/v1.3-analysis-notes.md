# Pilot 2 analysis notes for v1.3

Offline check of `proposal/v1.3-results-draft.md` against the per-task records in `pilot/results2`, done October 17, 2026. No model calls were made. Nothing under `results2` was edited by hand; `python report.py --results results2` was run once at the end, as section 12 asks, which appended one block to `report.md` (every earlier line byte-identical) and left `summary.json` byte-identical.

How the numbers were made. A script in the session scratchpad (`analyze.py`, not committed) loads every record through `report.load()`, uses `report.wilson` and `report.paired_bootstrap` (seed 0) so intervals match the report exactly, rescores intermediate texts with `checkers.score` (for code tasks that runs the candidate against the tests locally, as the harness does), and reads `results2/calls.jsonl` for anything the records do not hold. Fisher's exact test is computed by enumeration of the hypergeometric table (the venv has no scipy). Seat letters are fixed by `config.json` order in every record: A = Claude Sonnet 5, B = GPT-5.6 Luna Pro, C = Gemini 3.8 Flash, D = DeepSeek V4 Pro.

What the records do not hold (each section says where this bites):

- Per-component drafts. The step log keeps the assembled first draft (step 3, `draft`) and each revision's full text (step 4, `answer`), not the drafts seats wrote per component and not the compare verdicts.
- Which challenge a reviser accepted. The step-4 revision entry stores counts (`accepted`, `rejected`), not which challenge, so a critique can be tied to a revision only at the round level, or exactly when one seat raised every challenge of that round.
- Which seat answered the hub. Step-5 entries hold the questions, replies and open list, not the replier; it is recovered from `calls.jsonl` (the successful `panel-reply` calls of the task's final run, in order).
- The hub's corrected text per batch. Only the final answer is stored, with a cumulative `corrected` flag per batch.
- The catalogue text the hub read. Not logged anywhere. `calls.jsonl` has the whole hub-ask prompt's token count, nothing finer.
- The pre-hub answer text. `pre_hub_correct` is stored; the text is the last revision's (verified: in every c, c2 and d record without a hub correction the last logged text equals the final answer, 0 exceptions).
- Earlier runs of the same task. A record holds its final run only; `calls.jsonl` holds every call, including the cleared trial and the attempts that ended in an error.

## 12. Report lines

`report.py` gained one function, `panel_stage_lines`, called after the falsification readout and before the files are written, and a `fisher_exact` helper (enumeration, no scipy). Everything before the new block is unchanged: regenerating the committed `results2/report.md` into a scratch copy with the old code gave an identical file, and the new run's diff against the committed file is the appended block only (55 lines); `summary.json` is byte-identical. The new block prints, for every panel condition present: first-draft, pre-hub and final counts with the wrong-draft ids; critique-only flips and hub-only flips with ids; pairwise first-draft and final flips with ids; accuracy by agreement with Fisher's exact test; flagged releases by reason with accuracy, wrong ids, overlaps and Fisher's test for flagged vs unflagged; hub questions per task with the count at the budget; checks run, failed, by kind, with each failed check's task, pre-hub and final state and whether it blocked release.
